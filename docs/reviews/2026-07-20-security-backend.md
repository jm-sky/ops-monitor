# Security Review: ops-monitor FastAPI backend

**Status:** `done`
**Created:** 2026-07-20
**Scope:** `backend/` — auth, 2FA/WebAuthn, OAuth, authorization, CLI, config/middleware, monitor module
**Reference bar:** `zbory-chwz/docs/reviews/2026-07-10--church-platform-review.md`
**Method:** static read of the code as deployed on the VPS. No files modified. Backport claims in `.docs/backport-progress.md` were checked against the actual code, not trusted.

---

## Summary / Verdict

The shared-core security backports the matrix marks ✅ for ops-monitor are, for the most part, **genuinely present**: bcrypt with no passlib, a thorough GDPR `delete_user`, `iss`/`aud` enforcement on the primary tokens, session hardening (blacklist + JTI + `token_version`), and the WebAuthn RP-ID/FRONTEND_URL fallback are all real. However, the review found **one broken security control the matrix implies is done (WebAuthn assertion verification is a stub), a secrets-exposure IDOR unique to this app's monitor module, an admin-authorization protection that is enforced in one router and bypassed in a parallel one, and rate-limiting that cannot be relied upon.** None of the shared-core backports are outright fabricated, but "WebAuthn ✅" is only half-true.

| Area | Assessment |
|------|-----------|
| Password hashing (bcrypt, no passlib) | ✅ Verified true (`auth_utils.py:14-21`, no passlib in deps) |
| JWT `iss`/`aud`, `type`, blacklist, `token_version` | ✅ Verified on primary tokens; ad-hoc 2FA tokens exempt (SEC-8) |
| GDPR `delete_user` (OAuth/2FA cleanup, PII zeroing, `tv++`) | ✅ Verified true and thorough (`auth/repositories.py:325-373`) |
| WebAuthn RP-ID prod fallback | ✅ Verified true (`webauthn_utils.py:26-39`) |
| WebAuthn passkey **authentication** | ❌ **Stubbed — no signature verification (SEC-3), discrepancy** |
| 2FA login end-to-end | ⚠️ **Functionally broken (fail-closed lockout) — discrepancy** |
| Authorization on core `/monitor` + `/users` | ❌ Secrets IDOR (SEC-1) + owner-protection bypass (SEC-2) |
| Rate limiting / brute-force protection | ❌ Spoofable key + never wired (SEC-4) |
| CORS / TrustedHost / security headers / secret-key strength | ✅ Solid, with production guardrails (`config.py:805`, `security_headers.py`) |

## Findings

| Sev | Location (file:line) | Finding | Recommendation |
|-----|----------------------|---------|----------------|
| **SEC-1 · High** | `modules/monitor/db_models.py:63,70` + `modules/monitor/router.py:119-125,133-152` | **Monitored-site secrets exposed to every authenticated user.** `SiteDB.to_response()` includes `token` (the bearer token ops-monitor uses to poll each target's `/health`+`/system`) and `teamsWebhookUrl`. `GET /monitor/sites` and `GET /monitor/site-statuses` are gated only by `CurrentUser` (any logged-in, email-verified account), not `AdminUser`. Since `POST /auth/register` is open, anyone who registers and verifies an email can read the polling bearer tokens and Teams webhook URLs for **all** monitored servers — credentials that can be used to hit those internal endpoints directly or to post into the org's Teams channel. | Drop `token` and `teamsWebhookUrl` from the response schema returned to non-admins (separate admin-only detail view), or gate the list/get endpoints behind `AdminUser`. |
| **SEC-2 · High** | `modules/users/router.py:177-206,208-225,228-245` vs `modules/admin/service.py:161-191` | **Owner / superadmin / protected-user deletion & demotion protections are bypassed via the `/users/*` router.** `AdminService.update_user`/`delete_user` correctly block a non-owner admin from assigning/removing the Owner role, deleting Owner/admin users, or deleting `PROTECTED_USER_EMAIL`. The parallel `users` module endpoints (`PATCH /api/users/{id}`, `DELETE /api/users/{id}`, `DELETE /api/users/{id}/hard`) are guarded only by `AdminUser` and call the repository directly with **none** of those checks. A regular admin can therefore hard-delete or demote the Owner/superadmin — directly contradicting the `SUPERADMIN_EMAIL` "cannot be deleted or demoted" invariant in `config.py:214-223`. `/users/{id}/hard` is a permanent physical delete. | Route all privileged user mutations through `AdminService` (or replicate the owner/protected-user/self guards in the `users` router), and require `OwnerUser` for hard-delete and for any Owner-role change. |
| **SEC-3 · High** (discrepancy) | `modules/two_factor/webauthn_service.py:356-376` | **WebAuthn passkey authentication is not actually verified.** `complete_authentication` looks up the passkey by `rawId`, confirms it belongs to the challenge's user, then `# TODO: Full WebAuthn verification ... For now, basic check`. There is **no** verification of the assertion signature against the stored public key, no challenge-signature check, no `rpIdHash`/origin check, and the signature counter is overwritten with no clone/regression detection (`:362-370`). Possession of the credential is never cryptographically proven — the `allowCredentials` list handed out by `initiate_authentication` (`:245-257`) contains exactly the `credential_id` needed to forge a "successful" assertion. The matrix marks WebAuthn ✅; registration-side verification is real (`webauthn_utils.py:130`), but the authentication path is a stub. *(Currently mitigated only accidentally — see the 2FA-lockout discrepancy below — not by design.)* | Implement `verify_authentication_response` (the `webauthn` lib is already a dependency) with challenge, origin, RP-ID, public-key and counter-regression checks before treating the passkey as verified. |
| **SEC-4 · Med-High** | `core/limiter.py:15-38,61-73` + `core/app_factory.py:179-213` | **Brute-force rate limiting cannot be relied upon.** (a) `get_client_ip` takes the **first** value of the client-controlled `X-Forwarded-For` header, so an attacker sends a fresh fake IP per request and each gets its own bucket — defeating the `10/minute` login and `5/minute` register/reset limits the code calls "CRITICAL." (b) `setup_limiter(app)` is **never called** anywhere in `create_app()`/`main.py`, so `app.state.limiter` is unset and the `RateLimitExceeded → 429` handler is never registered; limit breaches were never validated end-to-end and surface through the generic 500 handler with no `Retry-After`. | Behind Caddy, derive the client IP from the **rightmost/trusted** proxy hop (or `request.client.host`), not the leftmost XFF value. Call `setup_limiter(app)` in `create_app()` and add a test asserting a 429 on the login limit. |
| **SEC-5 · Medium** | `modules/two_factor/crypto_utils.py:89-112` + `two_factor/totp_service.py:346-351` | **Backup-code single-use guarantee is broken.** `verify_backup_code` normalizes the input (strips dashes, uppercases, re-inserts dashes) before hashing, but `mark_backup_code_used` hashes the **raw** user-submitted string. When a code is submitted in any non-canonical form (lowercase, or without dashes — both accepted by `verify`), the "used" hash stored differs from the stored code hash, so the code is never marked consumed and passes verification again indefinitely — including at login via `verify_totp_login` → `verify_code(mark_used=True)`. | Normalize the code once (canonical form) and use that same canonical hash for both the membership check and the used-marking. |
| **SEC-6 · Medium** | `modules/auth/router.py:584-631` + `auth/schemas.py:213-220` | **OAuth callback does no server-side CSRF/state validation and leaks exception text.** `OAuthCallbackRequest` carries a `state` field and the endpoint docstring claims "CSRF protection via state parameter," but `state` is never read or validated server-side (it is not persisted at `/oauth/auth-url`). CSRF integrity of the OAuth login depends entirely on the frontend sessionStorage comparison; there is no PKCE. The handler also returns `detail=f"OAuth authentication failed: {str(e)}"` (`:628-630`), reflecting raw internal error text to the caller. | Either bind state to a server-side/HttpOnly value and verify it on callback, or remove the misleading docstring and document the SPA sessionStorage contract explicitly. Return a generic error message and log `str(e)` server-side only. |
| **SEC-7 · Low-Med** | `api/router.py:30-37` + `modules/users/router.py:116-154` | **Info disclosure.** The unauthenticated `GET /api/health` returns the raw DB exception string as `components.database.reason` (`str(exc)`), which can leak driver/DSN/host detail on failure. Separately, `GET /users/{id}/public` (no auth dependency) returns `isAdmin`/`isOwner`/`isPremium` for any user with a public profile, exposing the privilege topology and allowing user-ID existence probing (404 vs 403). | Return a static `"failed"` with no `reason` on the public health endpoint (keep detail behind the token-guarded `/health/details`). Drop the role flags from the public-profile response. |
| **SEC-8 · Low** | `two_factor/totp_service.py:83-97`; `webauthn_service.py:72-86`; `two_factor/auth_utils.py:78-88` | **Ad-hoc JWTs skip the `iss`/`aud` guardrails** applied to the main tokens (`auth_utils.py:119-125`). The `2fa_setup`, `passkey_registration`, and `2fa_verification` tokens are decoded with a bare `jwt.decode` (signature + `type` only). They share `SECRET_KEY`; if a sibling core-family app ever shares a key, these are cross-replayable. TOTP codes are also not burned after use, so they are replayable within the validity window. | Route these through a common decode helper that enforces `iss`/`aud`, and record the last-used TOTP timestep to prevent in-window replay. |

## Backport-matrix discrepancies (called out explicitly)

- **WebAuthn "✅" is only half-implemented** — registration is properly verified, authentication is a stub (SEC-3).
- **2FA login is functionally broken (fail-closed) — a correctness discrepancy behind the 2FA ✅ claims.** Neither `verify_totp_login` (`two_factor/service.py:141-146`, mints tokens with no `tfaVerified`) nor `complete_passkey_authentication` (returns `{success, userId, passkeyId}`, not tokens) ever issues an access token with `tfaVerified=True`. `_verify_user_token` (`auth/dependencies.py:168-176`) then rejects every request from a 2FA-enabled user with 401 "2FA verification required." Net effect: **enabling TOTP or a passkey locks the user out.** This fails safe (no bypass), but it means the 2FA flows are not actually exercisable — which is also why SEC-3 is not directly reachable as a live login bypass today.
- **Verified genuinely true:** bcrypt/no-passlib; GDPR `delete_user` (anonymizes email/name, nulls password/reset/verification/OAuth/avatar/`openrouter_api_token`, `token_version += 1`, deletes OAuth connections + TOTP + passkeys, blacklists sessions — `auth/repositories.py:325-373` + `auth/service.py:479-568`); `iss`/`aud` on primary tokens; session blacklist/JTI/`token_version`; WebAuthn RP-ID prod fallback; the `AuthServiceWith2FA` `super().__init__` fix. Production config guardrails (`validate_production` rejecting DEBUG/`*` CORS/empty ALLOWED_HOSTS, secret-key strength validation) are present and good.

---

## Overall risk assessment

For continued **soft-launch / pre-production** use with only trusted internal operators holding accounts, the app is **not catastrophically exposed** — the two most serious items (SEC-3 WebAuthn stub, and the 2FA lockout) are gated by the broken 2FA issuance and by admin-only reach, and there are no real external users yet. However, **SEC-1 and SEC-2 are genuine blockers to widening access**: because `POST /auth/register` is open, any self-registered, email-verified account can read every monitored server's polling bearer token and Teams webhook URL (SEC-1), and any admin can permanently delete or demote the Owner/superadmin the config is supposed to protect (SEC-2). Combined with rate limiting that is both key-spoofable and never wired (SEC-4), treat SEC-1, SEC-2, and SEC-4 as must-fix before this leaves the "no real external users" phase, fix the SEC-3/2FA pair before advertising 2FA as a feature, and address SEC-5–SEC-8 as fast-follows. All findings are reversible code-level fixes; none require infra or schema changes beyond what's already present.
