# Review: ops-monitor — code quality (backend + frontend)

**Status:** `done`
**Created:** 2026-07-20
**Scope:** `backend/app/`, `backend/cli/`, `backend/tests/` (FastAPI); `src/` (Vue 3). Read-only review, no changes made.

---

## Verdict

ops-monitor lives up to its reputation as the most mature member of the `gear-stack` family for CLI/auth ergonomics, and the frontend (Vue modules, composables, i18n, TS typing) is genuinely solid — minimal `any`, consistent module structure, business logic mostly pushed into composables/services as the project's own `CLAUDE.md` mandates. The backend's domain code (`modules/monitor`) is clean and readable.

The problems are concentrated in three places: **(1) a live bug** — the admin "create user" API endpoint is unreachable/broken; **(2) infrastructure that duplicated itself instead of being reused** — a second, mostly dead exception-handling stack, two independent `UserRepository` implementations, and a settings module with no repository/service layer at all; **(3) a test-coverage cliff** — the alerting engine, poller, WebAuthn, OAuth, and the entire 3,456-line CLI have zero tests, while ~40% of all backend tests cluster around auth utils alone. None of this is exotic; it's the kind of drift you'd expect from iterative feature work without a periodic cleanup pass, which tracks with this being the project's first formal review.

## Findings

| Severity | Location | Finding | Recommendation |
|---|---|---|---|
| **High** | `backend/app/modules/users/router.py:39-51` + `backend/app/modules/users/repositories.py:70-81` | `POST /api/users/` (admin "create user") calls `UserRepository.create_user()`, which unconditionally raises `NotImplementedError` ("must be done through auth module endpoints"). The endpoint is documented and routed but will always 500. No test exercises it. | Either remove the endpoint/route (and its schema `UserCreate`) or wire it to `auth.repositories.UserRepository.create_user` + a password/invite flow. Add a test that would have caught this. |
| **High** | `backend/app/modules/auth/repositories.py` (class `UserRepository`) vs `backend/app/modules/users/repositories.py` (class `UserRepository`, wraps the former via composition) | Two independent `UserRepository` classes for the same `UserDB` entity with inconsistent APIs: auth's `delete_user(user_id, soft_delete=True)` uses one flag; users' module instead exposes two separate methods `delete_user()` / `hard_delete_user()`. Two different `User` domain models (`auth.models.User`, `users.models.User`) require a manual field-by-field translation (`_auth_user_to_users_user`). Easy for the two to drift on business rules (e.g. email normalization, soft-delete semantics). | Collapse to one `User` model + one repository; expose an admin-facing service on top of it instead of a second repository shim. If the adapter is kept, standardize the soft/hard-delete signature between the two. |
| **High** | `backend/app/exceptions/exception_handler.py`, `backend/app/exceptions/custom_exceptions.py` (whole files), vs. `backend/app/core/app_factory.py:216-298` | Dead exception-handling stack: `AppException`/`BadRequestError`/`UnauthorizedError`/`ForbiddenError`/`NotFoundError`/`ConflictError` and their handler (`http_exception_handler`, `validation_exception_handler`) are exported from `app/exceptions/__init__.py` but never registered on the `FastAPI` app and never raised by any module (each module defines its own plain-`Exception` hierarchy instead — `AuthException`, `LogError`, `TwoFactorError`, ad hoc `Exception` in `users/exceptions.py`). The app actually uses a second, different set of handlers defined inline in `app_factory.register_exception_handlers()`. Two parallel, divergent error-handling policies exist; only one is live. | Delete the orphaned `app/exceptions/exception_handler.py` + `custom_exceptions.py` (or wire them in and delete the inline duplicate in `app_factory.py`). Pick one exception base class per module going forward so error handling doesn't silently fork again. |
| **Medium** | `backend/app/modules/monitor/alerts/dispatcher.py` (whole file, 273 lines) + `backend/app/modules/monitor/scheduler.py` + `backend/app/modules/monitor/service.py` | Core alerting/polling logic — quiet-hours math (`_is_in_quiet_hours`), cooldown/dedup (`_should_fire`), channel filter matching (`_matches_filters`), the poller loop, and `MonitorService._poll_health/_poll_system/_poll_ssl` — has **zero unit tests** (`grep` for `dispatcher`/`scheduler` across `backend/tests/` returns nothing). These are pure, easily-testable functions implementing the app's primary purpose (Teams/Telegram/email alerts). A bug in `_is_in_quiet_hours`'s midnight-wrap logic or `_should_fire`'s cooldown math would silently suppress or spam alerts with no test to catch it. | Add unit tests for the pure helpers in `dispatcher.py` first (cheap, high value: no DB/network needed), then an integration test for `poll_due_sites`/`_poll_health` with a mocked httpx transport. |
| **Medium** | `backend/app/modules/monitor/service.py:121-232` (`_poll_health`, `_poll_system`, `_poll_ssl`) | The three poll methods are ~90% identical boilerplate (build headers/URL → try/except `httpx.TimeoutException`/`HTTPStatusError`/`Exception` → save via `SnapshotRepository` → `cleanup_old` → `dispatch_if_changed`), repeated three times with only the inner fetch/parse differing. | Extract a shared `_poll_and_record(site, snapshot_type, fetch_fn)` helper; keeps the per-type parsing logic but removes ~60 duplicated lines and reduces the chance the three drift (e.g. only `_poll_health` currently computes `meta_mismatches`). |
| **Medium** | `backend/app/modules/settings/router.py` (whole file) | Only module with **no `repository.py` and no `service.py`** — raw SQLAlchemy `select`/`db.add`/`db.commit` and an authorization rule (`high_quality` mode requires admin, line 90-94) live directly in the router, unlike every sibling module (`auth`, `admin`, `logs`, `monitor`, `two_factor`, `users` all separate persistence/business logic from the router). No tests exist for this module either. | Extract `SettingsRepository` (get-or-create) and a thin `SettingsService` for the authorization rule, matching the pattern used elsewhere; add a test for the admin-only `high_quality` gate specifically, since that's the one bit of actual business logic in the file. |
| **Medium** | `backend/cli/commands/users.py` (1,444 lines — largest file in the backend by ~1.7x) | God file mixing CLI presentation (Typer options, Rich `Panel`/`Table`) with data access. Two concrete duplications inside it: (1) the "role → display string" ternary chain is repeated near-verbatim at lines 158-166, 316-320, 956-973, 1133-1141, 1291; (2) the `async for db in get_db(): ... break` session-boilerplate pattern is repeated identically in 8 separate helper functions. `_users_toggle_owner_async` (line 992-994) also calls both `_toggle_owner_in_db` and `_toggle_admin_in_db`, causing two separate DB round-trips/commits where one call would do. | Extract a `format_role_display(user) -> str` helper and a small `async with get_db_session() as db:` context manager to cut this file by a few hundred lines and remove the double-write in toggle-owner. This is the file the family's `--wide`/`--detailed` CLI features were sourced from, so keep behavior but shrink the surface. |
| **Medium** | `backend/app/modules/auth/service.py:311` | `os.getenv("ENVIRONMENT", "production").lower() == "development"` gates whether the password-reset token is logged in plaintext. This bypasses `settings.is_development()` (already defined on `Settings`, used everywhere else, and validated/typed via `Environment` enum). If `ENVIRONMENT` and the Pydantic-settings-resolved `app.environment` ever disagree, a plaintext reset token could be logged in what the rest of the app considers production. | Replace with `settings.is_development()` for a single source of truth. |
| **Low** | `backend/app/modules/auth/service.py:565-566` | Stale `# TODO: Invalidate all user sessions/tokens` / `# TODO: Delete related data (2FA, passkeys, etc.)` comments sit directly below code that already does both (`token_blacklist_service.blacklist_all_user_tokens(...)` at 546-549, `two_factor_repository.disable_totp`/`delete_all_passkeys` at 531-532). Misleading for future contributors triaging account-deletion behavior. | Delete the stale TODOs. |
| **Low** | `backend/app/modules/monitor/repositories.py`, `backend/app/modules/logs/repositories.py`, `backend/app/modules/admin/repository.py` vs `backend/app/modules/auth/repositories.py` | Repository pattern applied inconsistently in shape even where present: `auth`'s `UserRepositoryInterface` is an `ABC` with `@abstractmethod`, while `two_factor`'s equivalent is a structural `Protocol`. Neither is wrong, but a contributor moving between modules has to re-learn which interface style applies. | Not urgent — worth a one-line convention note in `CLAUDE.md`/`SHARED_CORE.md` so new modules pick one style rather than alternating. |
| **Low** | `src/modules/auth/composables/useAuth.ts:74,86`, `src/modules/auth/guards/authGuard.ts:64` | `(response.user as any).avatarUrl \|\| response.user.avatarUrl` casts to `any` purely to immediately fall back to the same, already-typed property access. The cast does nothing functionally. File-level `/* eslint-disable @typescript-eslint/no-explicit-any */` at the top of `useAuth.ts` exists only because of these two lines. | Delete the `as any` casts and the file-level eslint-disable; `avatarUrl` is clearly already on the `User`/login-response type. |
| **Low** | `src/modules/monitor/pages/MonitorPage.vue:89-204` | Non-trivial filtering/grouping/search logic (`compareSiteInGroup`, `compareSiteInServerGroup`, `matchesSearch`, `normalizeSearchValue`, `groupedStatuses`, `filteredGroupedStatuses`) lives inline in the page component (389 lines total), while sibling concerns in the same module are already extracted into composables. Inconsistent with the project's own stated rule ("business logic in service classes, not stores or components") and makes this logic unreachable for unit tests. | Extract into a `useMonitorSiteFiltering(statuses)` composable alongside the module's other composables. |
| **Low** | `backend/tests/` distribution | 131 test functions total for ~21,300 lines of backend code (`app/` + `cli/`), but 39% of those are in `test_auth_utils.py` + `test_auth_service.py` alone. Zero tests reference `dispatcher`, `scheduler`, `webauthn`, or any CLI module. | Not asking for uniform coverage, but the riskiest/most-changed code (alerting, CLI user management, WebAuthn) is currently the least protected. Prioritize per the dispatcher finding above. |

## Overall health & ROI

The codebase is in better shape than the (partly stale) `docs/SHARED_CORE.md` suggests — the boolean-parsing duplication it flags is already fixed (`app/core/helpers.py::parse_bool_value`), and a production-config guardrail it says is missing (`Settings.validate_production()`) already exists and is called from `app_factory.lifespan`. That document is worth a refresh pass since it's actively misleading about the project's current state.

For actual ROI, fix in this order:
1. **The broken `POST /api/users/` endpoint** — a one-line-cause, five-minute fix (or deliberate removal) that currently means "admin creates user via API" silently 500s in what local docs call pre-launch/soft-prod.
2. **Delete the dead `app/exceptions/` stack** — zero behavior risk to remove, and it stops the next contributor from spending an hour figuring out which of the two error-handling systems is live.
3. **Add tests for `alerts/dispatcher.py`'s pure functions** — the highest risk-to-effort ratio in the repo: this is the app's actual product surface (Teams/Telegram/email alerting), the functions are pure and trivial to test, and there is currently no safety net at all under them.
4. Everything else (users/auth repository duplication, `cli/commands/users.py` size, settings module's missing service layer) is real technical debt but lower urgency — worth scheduling as a backport-style cleanup rather than urgent work.
